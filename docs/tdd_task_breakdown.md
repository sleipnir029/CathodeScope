## 1. Implementation Principles

### 1.1 RED / GREEN / REFACTOR Policy

Every task follows strict TDD discipline:

1. **RED**: Write the test(s) first. Tests must fail because the production code does not yet exist. Run `pytest` and confirm red. Commit the failing test(s) with message prefix `test:`.
2. **GREEN**: Write the minimum production code to make the tests pass. No optimization, no refactoring, no "while I'm here" changes. Run `pytest` and confirm green. Commit with message prefix `feat:` or `fix:`.
3. **REFACTOR**: Clean up production code (extract helpers, improve naming, add docstrings) while keeping tests green. Run `pytest` after every refactor step. Commit with message prefix `refactor:`.

**Hard rules**:

- No production code without a failing test first.
- No test written after the production code it tests.
- Each RED/GREEN/REFACTOR cycle is one atomic commit or a short sequence of commits.
- If a test is hard to write, the interface is probably wrong — redesign the interface, not the test.

### 1.2 Mocking Policy

| What to Mock | How | When Real |
|---|---|---|
| Materials Project API | Cached JSON fixtures in `tests/fixtures/mp_responses/` | Integration tests may optionally hit live API; CI always uses fixtures |
| MACE calculator | Mock ASE calculator returning pre-computed energies/forces | Integration tests only; never in unit tests |
| Filesystem (artifact store) | `pytest` `tmp_path` fixture | All real runs use `artifacts/` directory |
| Workflow engine (benchmark tests) | Mock engine returning predetermined `WorkflowResult` | Integration tests use real engine |
| Time / UUID generation | `freezegun` or manual injection for deterministic IDs/timestamps | Never mock in integration tests |

**Anti-pattern**: Never mock pymatgen's `Structure` class or `SpacegroupAnalyzer`. These are fast, deterministic, and part of the domain logic being tested.

### 1.3 Fixture Policy

All fixtures live under `tests/fixtures/` and are committed to version control.

| Fixture Directory | Contents | Source |
|---|---|---|
| `tests/fixtures/mp_responses/` | `mp-22526.json`, `mp-19017.json`, `mp-18767.json` | One-time capture from live MP API via `scripts/capture_fixtures.py` |
| `tests/fixtures/structures/` | `licoo2_conventional.json`, `lifepo4_conventional.json`, `limn2o4_conventional.json` | pymatgen `Structure.as_dict()` output after normalization |
| `tests/fixtures/configs/` | `default_config.json`, `strict_config.json`, `relaxed_config.json` | Hand-written test configurations |
| `tests/fixtures/expected_outputs/` | Golden `WorkflowResult`, `ReportRecord`, `BenchmarkRow` JSON files | Generated by first passing run, then frozen |

**Fixture generation rule**: Capture real fixtures once using `scripts/capture_fixtures.py`. Commit them. Never regenerate automatically in CI.

### 1.4 Reproducibility Policy

- All tests must be deterministic. No random seeds without explicit seeding.
- UUIDs in tests use a deterministic generator (inject a factory function, not `uuid.uuid4()` directly).
- Timestamps in tests use frozen time (`2026-01-01T00:00:00Z` as the canonical test timestamp).
- Floating-point comparisons use `pytest.approx()` with documented tolerances.
- Environment variables `OMP_NUM_THREADS=1` and `MKL_NUM_THREADS=1` set in CI for deterministic MACE execution.

### 1.5 Definition of Done (Per Task)

A task is done when ALL of the following are true:

1. All tests listed in the task are written and passing.
2. `ruff check` passes with no errors on all new/modified files.
3. `mypy --strict` passes on all `cathodescope/models/` files; `mypy` passes on all other new files.
4. All public functions have docstrings.
5. All pydantic models have `model_config` with `json_schema_extra` examples where appropriate.
6. No `# TODO` comments remain (capture as deferred tasks instead).
7. Import rules from `dependency_graph.md` Section 6 are respected (no cross-tool imports, no validation importing tools, etc.).

## 6. Stop Conditions

These are mandatory pause points. Do NOT proceed past a stop condition until it is explicitly resolved.

### SC-01: MACE Installation Verification

| Field | Value |
|---|---|
| **When** | Before running T-20 (LiCoO2 integration test) |
| **What to check** | MACE-MP-0 installs on the dev machine; a single-point energy calculation on LiCoO2 completes without error |
| **Resolution if failed** | Debug PyTorch/MACE compatibility. Try CPU-only install. Check `mace-torch` version against `tech_stack.md` assumptions. Document the working environment. |
| **Who resolves** | Developer |
| **May not proceed until** | MACE single-point energy returns a finite value for the LiCoO2 fixture structure |

### SC-02: LiCoO2 Lattice Accuracy

| Field | Value |
|---|---|
| **When** | After T-20 passes |
| **What to check** | LiCoO2 relaxed lattice parameters deviate < 2% from MP reference (a ~ 2.836 Å, c ~ 14.083 Å). Volume deviation < 5%. |
| **Resolution if failed** | Check normalization (primitive vs. conventional cell mismatch). Check MACE model version. Check relaxation parameters (fmax, max_steps, optimizer). Compare against published MACE-MP-0 benchmarks. |
| **Who resolves** | Developer + scientific review |
| **May not proceed until** | Lattice deviations confirmed < 2% or documented explanation for deviation |

### SC-03: Evidence Label Audit

| Field | Value |
|---|---|
| **When** | After T-13 (evidence labeler) completes |
| **What to check** | All 8 MVP evidence labels match `scientific_validity_matrix.md` Section 3 Part A exactly |
| **Resolution if failed** | Update `cathodescope/validation/evidence.py` to match the matrix. Re-run evidence tests. |
| **Who resolves** | Developer + cross-check against docs |
| **May not proceed until** | Every label assignment matches the authoritative validity matrix |

### SC-04: Report Wording Audit

| Field | Value |
|---|---|
| **When** | After T-16 (Markdown renderer) completes |
| **What to check** | Generated Markdown report matches the mock excerpt format in `scientific_validity_matrix.md` Section 5. All 10 wording rules enforced. No disallowed words present. |
| **Resolution if failed** | Update `cathodescope/reporting/markdown_report.py` templates. Add missing wording checks. Re-run report tests. |
| **Who resolves** | Developer + scientific review |
| **May not proceed until** | Report format verified against the mock excerpt |

### SC-05: Benchmark Results Review

| Field | Value |
|---|---|
| **When** | After T-24 (benchmark integration test) completes |
| **What to check** | At least 2/3 materials achieve Full Success. Third achieves at least Partial Success. All metrics from `benchmark_spec.md` Section 4 populated for every material. Results make physical sense. |
| **Resolution if failed** | Investigate the failing material. Check MACE parameters. For LiMn2O4 Jahn-Teller effects: document as expected Partial Success, do not lower thresholds. For unexpected failures: debug the pipeline. |
| **Who resolves** | Developer + scientific review |
| **May not proceed until** | Benchmark passes 2/3 criterion or failures are scientifically documented |

### SC-06: Reproducibility Verification

| Field | Value |
|---|---|
| **When** | After T-24 (benchmark integration test) — same as SC-05 |
| **What to check** | Re-running the benchmark produces the same result category for each material. Lattice parameter deviations agree within 0.1% between runs. Same space groups reported. |
| **Resolution if failed** | Set `OMP_NUM_THREADS=1` and `MKL_NUM_THREADS=1`. Investigate floating-point non-determinism in MACE or optimizer. Pin all thread counts. Document reference platform in provenance. |
| **Who resolves** | Developer |
| **May not proceed until** | Two consecutive runs produce consistent result categories |
